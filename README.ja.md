# cuj-to-slo

[English](README.md) | 日本語

利用者、クリティカルユーザージャーニー（CUJ）、要求を出発点に、利用時の品質要求と KPI、機能要件、製品とデータの品質要求を順に導き、最後に SLI と SLO を備えた非機能要件にまとめるエージェントスキルです。各項目は前の段階の項目にさかのぼれるので、どの SLO からでも、それが守っている利用者までたどれます。

[chain-summary-html](https://github.com/Taro000/chain-summary-html) で 1 ページにまとめた例: [配車アプリ（日本語）](https://taro000.github.io/chain-summary-html/ride-hailing-full/docs/quality/summary.html)、[宿題提出サービス（英語）](https://taro000.github.io/chain-summary-html/homework-service-full-en/docs/quality/summary.html)。

## 4 つの段階

| 段階 | スキル | 入力 | 出力 |
|---|---|---|---|
| 1 | `cuj-to-quality-in-use` | 自分で用意した利用者、CUJ、要求 | 利用時の品質要求、手段の KPI |
| 2 | `quality-in-use-to-functional-requirements` | 段階 1 の出力 | 受け入れ基準付きの機能要件 |
| 3 | `functional-requirements-to-product-quality` | 段階 2 の出力と、利用者を経由しない要求（法令、標準・指針、セキュリティのリスク分析、開発方針・制約） | 優先順位を付けた製品とデータの品質要求 |
| 4 | `product-quality-to-slo` | 段階 3 の出力と、運用の事実（テレメトリ、トラフィック、ベースライン） | 非機能要件、SLI 定義書、仮の SLO、エラーバジェット方針、アラート（バーンレートのアラート、期限があるものは進み具合のアラート） |

段階 3 と 4 が自分で機能要件を加えることはありません。品質要求を満たすのに必要な機能が足りないときは、機能の提案を書きます。受け入れるかどうかは、段階 2 を再実行して決めてください。

## インストール

```sh
# 4 つのスキルすべてを、今のプロジェクトに入れる
npx skills add Taro000/cuj-to-slo

# インストールせずに、スキルの一覧だけを見る
npx skills add Taro000/cuj-to-slo --list

# 1 つのスキルだけを、Claude Code 向けに、すべてのプロジェクトで使えるように入れる
npx skills add Taro000/cuj-to-slo --skill product-quality-to-slo -a claude-code -g
```

## 使い方

段階ごとに別の依頼として、順番に実行します。

1. 「利用者、CUJ、事業の目標は次のとおりです: … 利用時の品質要求と KPI を導いてください。」
2. 「利用時の品質要求を機能要件にしてください。」
3. 「これらの機能について、製品とデータの品質要求を導いてください。法令の要求: …」
4. 「品質要求を非機能要件と SLO にしてください。ロードバランサのログがあり、購入手続きは 1 日に約 30 万件です。」
5. 段階 3 か 4 で機能の提案が出たら: 「段階 2 を再実行して、機能の提案に結論を出してください。」そのあと、新しく加わった機能について段階 3 と 4 を再実行します。

どのスキルもまずその段階の全体を下書きします。そのあとで、自信のなかった点を影響の広さ（どれだけの項目がそれに依存するか）と重大さ（下書きが間違っていたときの害）で評価し、どちらかが「高」の点だけを質問します。優先順位、目標値、方針も同じように評価し、質問したものはあなたの回答がそのまま決定になります。ただし、CUJ ごとに重視する品質要求とエラーバジェット方針の二つは、評価にかかわらず必ず質問します。それ以外の点は下書きのまま進めて仮定として記録し、最後に一覧で示します。目を通して、違うものがあれば直せます。どの判断にも根拠の印として入力・推定・仮定・確認済み（YAML では `stated`・`inferred`・`assumed`・`confirmed`）が付くので、どれが入力から来たもので、どれをエージェントが判断し、どれがまだ誰にも確かめられていないのかを見分けられます。

各段階は長い作業です。中規模の製品なら段階ごとに数十件の項目が出るので、それを見直し、優先順位と目標値についての質問に答える時間を見込んでください。その回答こそがこの作業の目的です。

このスキルが書くのは、システムが何をどれだけうまくしなければならないかで、どう実現するかではありません。プラットフォーム、製品、インタフェースの名前やプロトコル、データの置き場、仕組み、測定の道具は選ばず、それについて質問もしません。入力にそうした判断が含まれていたら、設計のために `context.yaml` に残し（たとえば姉妹スキルの [req-to-design](https://github.com/Taro000/req-to-design) が読みます）、要求には入れません。設計が変わっても、要求を書き直さずに済むようにするためです。

報告書と各項目には今の状態だけを書き、履歴は git に任せます。どのスキルも実行の最後に、自分が書いたファイルを変更の理由を書いたメッセージでコミットし、次の実行ではそこからの差分を読みます。

質問は依頼に使った言語で、成果物はプロジェクトのドキュメントの言語で書きます。スキル本体は英語で書かれています。

YAML のキーと ID は英語で固定しています。どの段階もほかの段階のファイルを読めるようにするためです。

## スキルがしないこと

- 目標値を上から押しつけること。SLO の目標値は、示された数値やベースラインをもとにした仮の値から始まります。重要なものは質問し、それ以外は暫定の決定として記録します。
- 数値をでっち上げること。入力にないしきい値や目標値は、段階 4 が根拠を添えて仮の値を提案するまで、名前の付いた未定の値のままにします。
- 法令や標準が求める内容を、一般的な知識で補うこと。名前だけが示されて内容がわからないときは、スキルが質問します。
- 事業の優先順位を代わりに決めること。優先順位、目標値、対象外にするもの、エラーバジェット方針は事業の判断です。CUJ ごとに重視する品質要求とエラーバジェット方針は必ず質問し、ほかは影響の広さか重大さが「高」のものを質問し、それ以外は暫定的に採用して仮定として記録します。決まったものとして示すことはありません。
- 設計を決めること。プラットフォーム、製品、インタフェースの名前やプロトコル、データの置き場、仕組み、測定の道具は設計に任せます。
- 業務手順、運用、教育についての要件を書くこと。それでしか満たせないニーズがあるときは、報告書にその旨を 1 行だけ書きます。

## メンテナンス

`references/conventions.md`、`references/artifacts.md`、`references/glossary.md` は、どのスキルでも同じ内容です。`npx skills add --skill` は 1 つのスキルのディレクトリしか入れないためです。編集は `shared/` で行い、そのあと次を実行します。

```sh
scripts/sync-shared.sh          # shared/ をすべてのスキルにコピーする
scripts/sync-shared.sh --check  # 内容の違うコピーがあれば失敗する
```
